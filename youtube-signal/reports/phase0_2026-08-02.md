## Premise 1 — transcripts fetch. PASS.

Two runs, six distinct videos (search results are not stable between runs, so the
second run drew a different sample — that is stronger evidence, not weaker).

| video | channel | snippets | words | yta | yt-dlp |
|---|---|---|---|---|---|
| `86AlV6174KI` | Trading with DaviddTech | 861 | 6,173 | OK | OK |
| `y_bsjZThP0o` | AI Pathways | 1,085 | 7,517 | OK | OK |
| `MJ2WL4ld3Fo` | The Moving Average | 265 | 1,998 | OK | OK |
| `UFZZPYI9si0` | Trades by Matt | 455 | 2,786 | OK | OK |

**Success rate: 6/6 on `youtube-transcript-api`, 6/6 on `yt-dlp`.**

- Zero occurrences of `IpBlocked`, `RequestBlocked`, or `PoTokenRequired`. The
  bot-detection layer the prompt warned about did not fire.
- Both paths return byte-identical snippet counts and word counts. They disagree
  only on the `is_generated` flag for `MJ2WL4ld3Fo` — cosmetic, not a fetch failure.
- Captions are auto-generated, so expect no speaker labels and no punctuation
  reliability. Timestamps are present and usable for the evidence requirement.

Both paths are kept. `youtube-transcript-api` is roughly 20x faster and is the
default; `yt-dlp` is the fallback and additionally returns duration, upload date,
view count and channel ID in the same call.

## Premise 2 — API key. FAIL.

`YOUTUBE_API_KEY` is not in the environment, not in user-scope environment
variables, and no `.env` exists at `~`, `~/kalshi`, `set1_overshoot/`, or
`~/crypto/`. Validity therefore untested. Setup steps are in `HANDOFF.md`.

**However, this blocks much less than the prompt assumes.** `yt-dlp` searches
YouTube and enumerates channel uploads with no key and no quota at all — every
number in the table below was obtained that way. The 3,200-unit search budget in
the Phase 1 plan may be replaceable with 0 units.

Not yet established: whether keyless search can reproduce `order=date` and
`publishedAfter`, which query family **F3 Recent** depends on. That is the one
place the API key may still be genuinely required.

### The Nate Tokens case is a warning about the resolver, not just the name

Searching the bare string `"Nate Tokens"` resolves to **the wrong human**: `AI News
& Strategy Daily | Nate B Jones`, 309k subs, median 59k views, at 6/12 top hits and
rank 0. That is a confident, plausible, wrong answer.

It was caught only because the prompt's own description (~30k subs, ~2k views)
contradicted it. The correct channel — **Nates Tokens**, 30.2k subs, median 1,400
views — matches that description closely and surfaced only once topic context was
added to the query (`Nates Tokens polymarket`).

All five handle guesses (`@natetokens`, `@NateTokens`, `@nate_tokens`,
`@NateToken`, `@thenatetokens`) return HTTP 404, so handle-probing would not have
rescued it either.

**Implication for Phase 5:** the recall test compares retrieved channel IDs against
these four. If it had been seeded with the wrong Nate, the test would have reported
a confident pass or fail about a creator nobody meant. Pin the channel IDs above;
do not re-resolve by name at run time.

Nates Tokens is also on-topic in the exact way the prompt hoped: recent uploads
include *Polymarket Copytrade Bot Speed Test*, *Polymarket Weather Trading Bot Built
With Claude*, *FREE Polymarket Backtesting Tool*, at 703 / 5,913 / 2,266 views.
